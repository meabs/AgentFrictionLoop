Friction Loop

Coding agents leave a one-line note when a repository's docs slow them down. Git hooks file each note against the commit it belongs to. Once a week the notes are grouped, so a person can fix the doc gap that keeps costing agents time.

How it works

Note

Agent reports a snag

Before finishing, the agent runs fbl-friction --origin conflicting-knowledge "…". Text is cut to 240 characters, control characters are removed, and anything that looks like a secret is dropped.

Record

Commit becomes a record

The post-commit hook runs in the background. It stores changed paths, line counts, which guidance files were touched and the session's notes as one JSON file on the hidden fbl-insights branch.

Sync

Branch travels with the repo

The pre-push hook fetches, rebases and pushes that branch. If you are offline, records stay committed locally and go out with the next push.

Review

Weekly report, human fix

A scheduled GitHub Action groups the records and opens an issue only when the same gap keeps recurring. Nothing edits your docs automatically.

Hooks never block a commit or a push. If the tool fails, it logs to var/hook.log and exits quietly.

Where friction starts

Each note carries an origin: where the problem started, which decides who can fix it. The agent answers one question, "where did the problem start?", and the report groups notes by origin and names the remedy.

OriginExampleRemedy
repository-discoveryThe agent cannot find a contract that exists.Improve navigation or indexing: link it from AGENTS.md.
task-contextThe brief had no acceptance criterion.Improve how tasks are briefed. Usually fixed in the issue or prompt template, outside the repo.
execution-environmentA migration had to run before the tests.Fix the tooling, or document the prerequisite and its order as one runnable block.
verificationNo fast way to tell whether the change works.Improve tests or test infrastructure.
conflicting-knowledgeAn old design doc contradicts the code.Correct provenance or authority: update or remove the stale source and say which one wins.

--category still works, alone or together with --origin. When only --origin is given, the category is filled in for older readers (discovery → missing-doc, environment → setup, verification → test-order, conflicting → unclear-instruction, task-context → other). A note with an origin is grouped by it in the report; a note without one is grouped by its category, so existing records and AGENTS.md blocks keep working. Use --category environment alone for a machine fault no doc could prevent.

Task-context notes are reported as informational. The repository cannot fix them, so the report does not turn them into a docs recommendation. One note per root cause, three at most, and none when nothing went wrong.

Install

You need git and Python 3.10 or newer. On Windows, install Git for Windows, which supplies the sh that runs the hooks. The installer adds jsonschema with pip if it is missing.

macOS and Linux

./install.sh --repo ~/code/my-project --domain my-team

Then, in the project:

./.fbl/bin/fbl-friction --origin execution-environment "tests fail until make db-migrate has run"

Windows (PowerShell)

.\install.ps1 --repo C:\code\my-project --domain my-team

Then, in the project:

.\.fbl\bin\fbl-friction.cmd --origin execution-environment "tests fail until make db-migrate has run"

The installer copies the tool to ~/.local/share/fbl (%LOCALAPPDATA%\fbl on Windows), creates the launcher, installs both hooks, creates the insights branch and appends the reporting block to AGENTS.md for you to review and commit. It refuses to overwrite hooks you already have. Add --publish to push the branch to the remote, so everyone on the team shares one actor salt.

OptionEffect
--repoProject to instrument. Defaults to the current directory.
--domainTeam label stored with each record.
--adapterboundary (default), codex to also read local Codex sessions for token cost, or none.
--homeWhere the tool is copied.
--publishPush the insights branch to the remote.
--harnessExtra instruction files besides AGENTS.md: claude, copilot, cursor (all by default) or none.

--uninstallRemove this repository's hooks, .fbl/ and the insights worktree. Keeps the fbl-insights branch and the instruction files.

What the installer does

It changes three places: a shared tool folder, the project's .git directory, and AGENTS.md. Nothing is committed for you and nothing is pushed unless you pass --publish.

StepWhat happensWhere
1. CheckConfirms git and Python 3, finds the repository root, installs jsonschema with pip if it is missing.nowhere
2. Copy the toolReplaces the scripts, hooks, schemas and templates in the tool folder. Safe to re-run to upgrade.~/.local/share/fbl or %LOCALAPPDATA%\fbl
3. LauncherWrites fbl-friction (sh) and fbl-friction.cmd (PowerShell, cmd) that call the tool with the Python that ran the installer. Adds .fbl/ to .git/info/exclude, so it is never committed.<project>/.fbl/bin/
4. Insights branchCreates the orphan branch fbl-insights as a linked worktree, or adopts the one already on the remote..git/fbl/insights
5. HooksWrites post-commit and pre-push. Each exports the tool path and Python path and runs the tool in the background. An existing hook with different content stops the install with an error..git/hooks/
6. Publish (optional)With --publish, commits the shared actor salt and schema and pushes the branch.the remote
7. InstructionsAppends the friction block to AGENTS.md, .github/copilot-instructions.md and .cursor/rules/friction-reporting.mdc, and adds @AGENTS.md to CLAUDE.md. Files that already have a ## Friction reporting heading are skipped. Nothing is committed.project root

Hooks and the launcher live in .git and .fbl, which git does not share. Every clone needs its own install, including each teammate's.

What to configure in AGENTS.md

The file is AGENTS.md at the repository root. The installer adds the block below to AGENTS.md and the other instruction files; this section covers what you still have to check.

## Friction reporting

If something blocked or slowed you down, report it before finishing, even if you worked around it:

./.fbl/bin/fbl-friction --origin <origin> "<what happened and what fixed it, one line, no secrets>"

On Windows PowerShell or cmd.exe use `.\.fbl\bin\fbl-friction.cmd` instead.

Pick the origin by asking "where did the problem start?":
- repository-discovery: the contract, doc or entry point exists but you could not find it.
- task-context: the task lacked an acceptance criterion, constraint or input you needed.
- execution-environment: a prerequisite, migration, tool or service was missing or had to run in a certain order.
- verification: you could not run, or did not trust, the checks for your change (no documented test command, tests that need a prerequisite, flaky or missing fixtures, a suite too slow to run). Name the command that failed or was missing, even if you finished the task.
- conflicting-knowledge: two sources disagreed, or a doc contradicted the code. Say which one you trusted.

If `./.fbl/bin/fbl-friction` does not exist (cloud agents and CI have no launcher), add trailer lines to your commit message instead, one per note:

Friction[<origin>]: <what happened and what fixed it, one line, no secrets>

For a machine fault no doc could prevent (disk full, no network, permissions) use `--category environment` instead of `--origin`.

One note per root cause, at most 3 notes. Write nothing if nothing went wrong. You may instead add a commit trailer: `Friction[category]: text`.

Cloud agents and CI (experimental)

This path is experimental and not part of what 0.2.0 promises. An agent on a remote machine has no hooks and no .fbl/ launcher, because both live in your local .git. The AGENTS.md block tells it to put trailers in its commit messages instead:

Fix payment retry

Friction[repository-discovery]: could not find the payments contract
Friction[verification]: no single-test command documented

Copy templates/fbl-record.yml to .github/workflows/ and set FBL_TOOL_REPOSITORY, FBL_TOOL_REF and FBL_DOMAIN. On every push to main it records each new commit, trailers included, on the fbl-insights branch. A record a developer's machine already made is kept as it is.

As an APM package

The folder is also an Agent Package Manager package that ships one skill, friction-loop. The skill teaches agents when and how to file a note and bundles the installer.

apm install ./friction-tool --target claude
# or, once pushed to a git host:
apm install <owner>/friction-loop --target claude

APM only copies files, so it cannot install the hooks. After apm install, ask the agent to set the loop up, or run python .claude/skills/friction-loop/install.py --repo . yourself.

Command capture

Notes depend on the agent remembering to write one. Each harness's after-shell-command hook can also send the result to boundary.py command, which stores the command's leading words, its exit code and a kind (tests, lint, build, migrate, install, git, other). The record then shows failed commands and whether the first test run passed, even when no note was filed.

  • Output is discarded before anything is written. uv run pytest -x tests/secret_name.py is stored as uv run pytest.
  • Only recognised test, lint, build, migrate and install commands keep any words after the executable. mycli login hunter2 is stored as mycli. Quoted text is never split open.
  • The hook is silent and always exits 0, so it cannot disturb the agent.
  • The installer writes local configs (.claude/settings.local.json, .cursor/hooks.json, .github/hooks/fbl-commands.json), merges with settings you already have, leaves tracked files alone and excludes all three from git. --no-command-capture skips them.

What the live tests found

Each integration was checked against a live session, and each differed from its documentation or from a reasonable guess.

HarnessHooks usedWhat the live session showed
Claude CodePostToolUse, PostToolUseFailureThere is no exit_code field. A failure arrives as PostToolUseFailure with error: "Exit code N …"; only that number is read.
CursorpostToolUse, postToolUseFailureafterShellExecution fires for successes and failures alike with no exit code, so it is not used. Failure text sometimes names the code and sometimes is just the command's output, in which case 1 is recorded.
Copilot CLIpostToolUseA failed command still arrives as resultType: "success". The code is only in the text, <shellId: 0 completed with exit code 1>, so the parser reads that trailer and ignores the same words inside command output.

In all three, a failing python3 -m pytest and false were recorded with exit 1 and a passing command with 0, along with the session id. The tool never records an outcome it cannot see. The Copilot CLI runs a repository's hooks only in folders you have trusted; without that the hooks silently do nothing. Copilot's notes carry no session id, so they are linked to its commands by time.

Existing hooks and uninstalling

The installer stops rather than overwrite a hook it did not write, and updates its own hooks when you re-run it. If core.hooksPath is set (Husky and similar tools), it refuses, because that folder is tracked and the hooks hold machine-specific paths. Call the tool from your hook manager instead; hook manager support is on the roadmap.

python install.py --repo ~/code/my-project --uninstall

Uninstalling keeps your history of records (the fbl-insights branch) and the friction block in the instruction files, which you delete by hand.

What is stored

  • Changed file paths, line counts, a digest of the guidance files, and the friction notes.
  • A pseudonymous actor id: the first 12 hex characters of an HMAC of the lowercased author email, keyed with a salt stored on the insights branch. It lets the report count distinct people. It is not anonymous, because anyone holding the salt can test a guess.
  • Never prompts, transcripts, file contents, commit messages, author names or emails.

What Windows support changes

File locking uses msvcrt instead of fcntl. Git commands run with an empty hooks directory instead of /dev/null. Hook scripts get forward-slash paths and the Python interpreter recorded at install time. Agents on PowerShell or cmd use the fbl-friction.cmd launcher; Git Bash uses the shell one.
